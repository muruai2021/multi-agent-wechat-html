# 子Agent输出处理规范

本文档记录多Agent协作工作流中的子Agent输出处理规范，填补SKILL.md中未覆盖的运行时行为指引。

---

## 核心原则

主编（orchestrator）负责：
1. 调度子Agent任务
2. 收集子Agent输出
3. 汇总后交付

子Agent只负责：
1. 接收任务描述
2. 执行并输出内容
3. **不执行任何文件操作**

---

## 问题1：子Agent尝试执行文件操作

**症状**：写手Agent尝试运行bash/PowerShell保存文件，而不是直接输出文章内容。

**根因**：子Agent模板中包含了模糊的"输出格式"说明，容易被误解为需要执行文件保存。

**处理方式**：
- 在委托任务时，明确指令：**"禁止执行文件操作，只输出内容"**
- 如果子Agent仍尝试执行文件操作，主编应忽略其命令，直接从中提取内容

**预防**：agents.md写手模板已更新，新增"禁止执行文件操作"强制约束。

---

## 问题2：子Agent输出摘要而非完整内容

**症状**：子Agent输出"我将根据X素材撰写..."等计划性摘要，而非实际文章内容。

**处理方式**：
1. 提取摘要中的草案内容（通常在摘要后段）
2. 主编根据草案手动组装完整文章
3. 不要废弃整轮迭代

**示例**：
```
子Agent输出：
"我将根据素材和大纲撰写这篇公众号文章，并保存到工作目录。
$CONTENT = "## 标题\n正文..."
[System.Text.Encoding]::..."
```

**主编操作**：
1. 提取 $CONTENT 变量的实际内容
2. 如内容完整，直接使用
3. 如内容不完整，从摘要描述中还原关键段落
4. 手动组装后继续

---

## 问题3：评审后跳过了第4轮

**症状**：第3轮评审不达标后，委托第4轮修改，但评审步骤被跳过。

**处理方式**：
- 每轮迭代必须包含：写手修改 → 主编汇总 → 评审打分
- 即使时间较长，也不能跳过评审
- 主编应在每轮结束后主动调用评审Agent

---

## 问题4：文章结构偏离用户大纲

**症状**：子Agent（尤其是写手）在修改过程中大幅改动用户提供的原始大纲、金句、案例。

**处理方式**：
- 用户提供详细大纲/内容时，在委托任务时明确强调：**"严格遵循用户提供的结构、金句、案例"**
- 在传给写手的context中，原样保留用户原文，不得删改
- 写手的修改只应聚焦于：文字润色、逻辑优化、数据补充

**正确的修改范围**：
- ✅ 文字表述更流畅
- ✅ 补充具体数据
- ✅ 增加过渡句
- ✅ 优化段落节奏

**错误的修改范围**：
- ❌ 改动用户提供的金句
- ❌ 调整用户指定的文章结构
- ❌ 替换用户精选的案例
- ❌ 改变文章核心论点

---

## 问题5：研究员Agent返回空结果（仅tool trace，无实际内容）

**症状**：研究员Agent的leaf node执行了web search工具调用，但返回的summary只有工具调用记录，没有任何实际搜索结果或素材内容。

**识别特征**：
```
"task_index": 0,
"status": "completed",
"summary": "\"api_calls\": 1, \"duration_seconds\": 5.84, ...",
"tool_trace": []  // ← 实际搜索结果为空
```

**根因**：可能是Agent超时、工具返回格式异常、或任务描述不够具体导致Agent提前结束。

**处理方式**（按优先级）：
1. **直接使用用户提供的原始素材**（优先级最高）- 用户已提供高质量原始材料（播客笔记、访谈记录、干货内容），将这些材料作为主要来源，标注"素材来源：用户提供"
2. **不废弃整轮迭代** - 研究员失败不等于整轮失败，评估员可能已完成高质量输出
3. **主编手动补充事实细节** - 当文章缺少BenchMark名称、真实案例数据等关键事实时，主编应直接编辑补充，而非重新委托研究员
4. **避免重复调用同一Agent** - 如果研究员已超时一次，再次调用大概率重蹈覆辙

**预防**：
- 在委托研究员时，任务描述要非常具体（明确搜索关键词组合）
- 要求研究员在输出中先列出具体案例名称和数据，再做总结

## 问题6：评审步骤被完全跳过（虚假完成）

**症状**：主编在某步骤标记为"已完成"，但该步骤的Agent从未被调用。例如：声明"评审Agent打分：X/100"，但评审Agent的delegate_task从未执行。

**识别特征**：
- 查看todo列表，该步骤标记为completed但没有对应的delegate_task调用记录
- 评审报告的格式、语言风格与agents.md中评审模板描述完全一致（说明是人工写的而非Agent输出）

**处理方式**：
- 每一步都必须实际调用对应的Agent，不能用主观评估代替
- 如果确实需要跳过某步骤（如用户要求直接交付），必须如实告知用户："评审跳过了，以下是我对文章质量的主观评估"
- **绝对禁止**：捏造一个不存在的Agent评分或评审报告

## 主编操作检查清单

委托子Agent前检查：
- [ ] 任务描述是否清晰？
- [ ] 是否明确禁止文件操作？（写手任务）
- [ ] 是否包含用户提供的原始大纲/内容？
- [ ] 是否说明必须遵循的结构？

收集子Agent输出后检查：
- [ ] 输出是完整内容还是摘要？
- [ ] 是否包含文件操作命令？（如有，需提取实际内容）
- [ ] 是否遵循了用户的结构和内容？

---

## 术语说明

- **主编**：工作流协调者，即Hermes Agent本身
- **子Agent**：调研员、评估员、写手、评审等被调度的独立Agent
- **草案**：子Agent输出的未经最终整理的内容
- **组装**：主编从多个子Agent输出中提取、汇总、整理成最终交付物的过程

## v1.1 新增失败模式

### 失败模式 7：Step 1 用户未确认就启动调研

**症状**：主编收到主题后，没出"三件套"（标题 / 框架 / 钩子）就直接派调研员 + 评估员跑。

**根因**：主编跳过了"人在回路"门控。可能因为用户说"随便"、"你定"，主编就当真没确认了。

**恢复方法**：
1. 立即停止调研员 + 评估员（如已启动）
2. 撤回已收集的素材
3. 回到 Step 1 主编亲自出"三件套"，列出 2-3 个备选
4. 等用户明确说"OK / 用第 X 个 / 改 X"后才进 Step 2
5. **不要接受"随便"、"你定"、"都行"作为确认信号** —— 必须有具体选择动作

**预防**：主编的 Step 1 输出必须包含"请确认 / 请挑 / 请修改"的显式 prompt。

### 失败模式 8：写手提交"AI 风"长稿

**症状**：写手初稿大量命中禁用套话（"在这个时代"、"值得注意的是"、"综上所述"），段落超长（>200 字），无具体细节。

**根因**：写手 LLM 退回到"安全/通用"的输出模式。

**恢复方法**：
1. 评审维度五"人味与去 AI 味"直接判 0-5 分
2. 评审维度六"结构化可读性"按最长段落超 200 字直接扣 3-5 分
3. 写手根据评审反馈 + [article-writing-principles.md](article-writing-principles.md) 末尾的"去 AI 味清单"+"人味细节技法"重写
4. 重点检查：禁用套话 Ctrl+F 扫一遍、人味细节 ≥ 3 个、单段 ≤ 4 句

**预防**：
- 写手系统提示词里硬约束了 6 条禁用套话 + 7 条人味技法
- 自检清单第 5 步强制 Ctrl+F 扫禁用词
- 评审维度五是硬门槛（<12 分 = 整稿不及格）
